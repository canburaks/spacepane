# Performance review — 2026-10-06

Reviewed from source only, on Linux, on 2026-10-06: nothing was compiled, run, rendered or measured, and every runtime figure below is quoted from the repository's validation records (one Apple M5 Pro host, macOS 27.2, Xcode 27.0) or labelled as an inference. The dimension covers time to first useful content in the preview extension (cold and warm), the core pipeline, native rendering of text, source, JSON Outline, JSON Lines Records, tables, listings and Markdown, mode switching and restyling, memory, extension start-up, the CAD helper, thumbnails, live reload and scrolling. Verdict: the pipeline is bounded, cancellable and fast enough off the main thread, but the renderer does whole-document work on the main thread before the first frame (full TextKit layout, eager secondary models built with a slow JSON scanner, per-token styling, full restyles on no-op events), which keeps text, JSON, JSON Lines and source over the 200 ms warm target, and the program's only performance gate (decision 026 gate 11) cannot be measured as written.

## Current state

The code base already does much of what a fast Quick Look provider needs, and several costs were measured and removed on 2026-10-04.

- Parsing never runs on the main thread. `PreviewPipeline.preview` is `@concurrent`, and one serial `PreviewWorker` actor per pipeline bounds blocking work (`PreviewCore/PreviewPipeline.swift:22-47`). The extension's `preparePreviewOfFile` returns at once and does the work in a task (`Extensions/PrevPreviewExtension/PreviewViewController.swift:32-75`), as Apple asks (`docs/market/ux-research/2026-10-06-system-and-benchmarks.md:66`).
- Every request owns a budget and a cooperative deadline, checked at fine grain: every 512 bytes in the JSON scanner (`PreviewFormats/JSONSourceAdapter.swift:225-230`), every 1,024 scalars in validation (`PreviewCore/TextDecoder.swift:70-71`) and every 1,024 regex progress events in the privacy filter (`DefaultPrivacyFilter.swift:7-10`). Cancellation answers Quick Look immediately (`PreviewViewController.swift:100-105`).
- The privacy filter avoids its obvious traps: one scalar pass converts all UTF-8 offsets (`DefaultPrivacyFilter.swift:67-89`), a `memmem` prefilter skips value patterns whose literals are absent (`:124-127`, `:199-210`), and one contiguous UTF-16 copy serves every regex (`:97-99`). The core pipeline's warm p95 is 52.9 ms for JSON and 68.7 ms for JSON Lines (`docs/validation/release-pipeline-benchmark-2026-10-04.md:47-48`).
- The hidden-content scan costs one byte test on ASCII text and builds its line index only when a finding needs a line (`PreviewCore/HiddenContentScanner.swift:41-44`, `:210-237`).
- Tokenizers are single linear passes over UTF-16 arrays with token caps (`PreviewRenderers/Code/ProfiledSourceTokenizer.swift:4-15`, `JSONSyntaxTokens.swift:29-104`), and one style pass resolves the twelve role dictionaries per appearance (`NativeTextStylePass.swift:4-18`).
- The line-number gutter is viewport-bound: it binary-searches a cached line index and asks the layout manager only about visible glyphs (`LogicalLineNumberGutter.swift:62-91`).
- Initial layout is deliberately a single pass, including a scroller reservation that avoids a second wrap (`NativePreviewView.swift:694-726`), and `NativeInitialLayoutTests.swift` counts completed layout passes with a delegate. That is the harness a viewport-first change needs.
- Hidden source text is not restyled while Outline, Records or a table is shown (`NativePreviewView.swift:366-380`); outline items have object identity, root expansion is batched and cells are reused and restyled in place (`NativeOutlinePreviewView.swift:93-116`). These changes cut warm p95 JSON Outline switching from 193.8 to 16.0 ms and JSON Lines Records from 563.8 to 70.8 ms (`docs/validation/native-renderer-performance-2026-10-04.md:110-112`). The 951 ms Records maximum (`docs/validation/security-performance-2026-10-04.md:167`) belongs to the run before that change, whose slow path the follow-up record attributes to repeated root expansion and Swift object equality during item lookup (`native-renderer-performance-2026-10-04.md:11-13`); the optimized run's maximum is not reported. Remaining plausible tail causes are allocation growth across samples, main-thread scheduling at default QoS on efficiency cores, and the eager records build, which now sits in the initial stage.
- Rare or expensive things are lazy: derived mode views (`NativePreviewView.swift:728-745`), the geometry view (`:798-809`), the MIDI audio graph (`NativeMIDIPlayback.swift:49`), the CSV profile (`SafePreviewModes.swift:68-69`), the Invisibles model (`:94-95`) and the listing parse behind a cheap precheck (`Listings/SafeListing.swift:43-46`). The findings banner skips rebuilding unchanged rows (`Findings/NativeFindingsBanner.swift:61`).
- Thumbnails decide policy before any adapter is built, use a 256 KiB / 300 ms text budget and a 1 s hard timeout, and answer exactly once (`PreviewThumbnails/ContentThumbnailService.swift:72-95`, `ThumbnailLimits.swift:24`, `:36-41`, `ThumbnailRace.swift`). In Release a 250 KB source thumbnail took 44/46 ms median/maximum (`docs/validation/thumbnails-2026-10-05.md:47`). With content thumbnails off, a request costs one snapshot read and decode.
- The CAD importer is contained by process, time and memory: a 15 s CPU limit and a sampled 512 MiB physical-footprint guard in the child (`Native/CADWorker/main.cpp:22-37`), a 20 s parent deadline with SIGKILL and reaping (`PreviewCADFormats/CADWorkerProcess.swift:78-102`, `:173-188`), at most two imports per service process (`CADImportService.swift:24-25`), and a Metal view that is paused and drawn on demand (`PreviewRenderers/GeometryMetalRenderer.swift:34-35`).
- Live reload is event-driven (a vnode source on an `O_EVTONLY` descriptor), coalesced at 300 ms with a 2 s ceiling, and drops stale generations (`PreviewCore/PreviewSourceMonitor.swift:45-47`, `:146-167`; `PreviewLiveReloader.swift:96-112`).
- Both benchmarks are reproducible, record the environment, separate first-process from warm samples, keep raw samples and check that the sources are unchanged.

No step in the renderer's initial path is quadratic; the superlinear step is the concealment rebuild in the pipeline. Attribute edits in `applyStyling()` are inside one `beginEditing`/`endEditing` pair (`NativePreviewView.swift:556-570`); `textView.string =` is a separate edit before it. Repeated bridging appears in the per-token dictionaries, the foreign UTF-16 string that every later Swift pass iterates, and whole-text `textView.string` copies (PF-19).

**PF-01. Full-document layout before the first frame.** In the benchmark a 230 KB JSON file or a 145 KB source file spends 381 or 198 ms (warm p95) in display, layout and drawing after the pipeline, all on the main thread (`docs/validation/native-renderer-performance-2026-10-04.md:111`, `:115`); in Finder nothing of ours appears until it ends, zoom steps hitch, and live-resizing the panel or preview pane re-wraps the whole file per step. The cause is that `applyStyling()` sets `documentNeedsSizing` (`NativePreviewView.swift:575`) and `configureDocumentSize()`, called from `applyStyling()` and from every `layout()` (`:442-445`), runs `manager.ensureLayout(for: container)` (`:680`) to size the text view exactly from `usedRect`. That is glyph generation and typesetting for all 6,005 lines of the JSON fixture plus their wrapped fragments, not for the 35 or so on screen. The restyle stage, mostly this layout plus attribute work, costs 61 ms for text and 87 ms for source at warm p95 (`:110`, `:115`), and `NativeInitialLayoutTests` accepts one full re-wrap per width change (`resizingAReservedLayoutRewrapsOnceAtTheNewWidth`), which also covers decision 026's compact-density switch. The fix is to lay out the visible rectangle first (`ensureLayout(forBoundingRect:in:)`), size the document from the estimate the scroller reservation already computes (`:699-726`), let TextKit's background layout finish after first paint and set the exact height when `layoutManager(_:didCompleteLayoutFor:atEnd:)` reports the end; non-contiguous layout is an option for Go to Line and end-of-document jumps. TextKit 2 is a later spike, not the first step: the gutter (`LogicalLineNumberGutter.swift:63-91`), Go to Line (`Interaction/NativePreviewView+Interaction.swift:210-219`) and sizing use `NSLayoutManager` directly, a single `textView.layoutManager` access silently reverts a TextKit 2 view to TextKit 1, and `NativeInitialLayoutTests.swift:33-44` asserts TextKit 1 on purpose. The rule is the record's own: exact text, copy, find, wrapping, line numbers, selection and accessible last-line navigation must not change (`native-renderer-performance-2026-10-04.md:142-146`).

**PF-02. Eager secondary models and a slow safe JSON scanner.** A JSON file shown in Source pays for its Outline before the first frame, and a JSON Lines file pays for all 1,200 record trees. `display()` rebuilds `SafePreviewModes` whenever the presentation changes (`NativePreviewView.swift:298-299`), and the initializer derives every model regardless of the initial mode: the JSON outline (`SafePreviewModes.swift:197`), every JSON Lines record (`:194`), each line parsed separately (`:264`), the whole tree copied again only to renumber it (`:255`) and a localized format per record (`:258`), plus the String Catalog precheck for every `.json` (`Code/CodeSafeModes.swift:22`, `Code/SafeStringCatalogTable.swift:24`). The scanner behind them allocates a `Data` and a `JSONDecoder` for every key and string value (`SafeStructuredText.swift:108`) and evaluates a regular expression for every number, literal and concealment token (`:97-98`; the literal test does not short-circuit the regex). For the fixtures that is about 6,000 decodes and 1,201 regex evaluations for JSON and 7,200 and 2,400 for JSON Lines, all on the main actor; the same scanner builds Summary views for archives, databases, packages and data formats. The fix: decide availability from cheap facts (UTF-16 length within 262,144 units, node count within 20,000, which the pipeline's scanner already counts at `JSONSourceAdapter.swift:89-90`), build the model on first switch or in a background prefetch after first paint, decode escape-free strings inline with a fallback for escapes, and validate numbers by bytes as `JSONScanner.number()` does. The change stays inside `PreviewRenderers` unless the node count is carried in `TextPresentation`, which is a lead-owned contract change; invalidation must keep exact UTF-8 equality (`SafeStructuredText.swift:17-24`).

**PF-03. Full restyles on no-op events.** After the first frame, ordinary events cost a full restyle and a full relayout: returning from Outline or Records to Source (verified: `display()` reaches `applyStyling()` with unchanged content at `NativePreviewView.swift:381-394`, and `applyStyling()` re-applies every attribute and sets `documentNeedsSizing` without an early exit at `:550-583`), each zoom step (`Interaction/NativePreviewView+Interaction.swift:114`), an accessibility display-option notification (`:455-457`), a `providerName` change (`:78`) and every `viewDidChangeEffectiveAppearance` (`:437-440`). The deferred-styling design is real for hidden text (`:366-380`), but its saving is spent again on the way back, and the return path is not one of the benchmark's stages. In Finder the view is filled before Quick Look presents it, so if AppKit reports an appearance change when the view joins the host window, the initial styling and layout are paid twice; whether that callback fires there needs a Mac. The fix is a style signature (resolved typography and zoom, palette identity, syntax style and a content generation) that skips the storage pass and the layout when unchanged. No product rule is touched; `DeferredSourceStylingTests` and `NativeTextStylePassTests` already pin the required results.

**PF-04. Quadratic, uncancellable concealment.** Ordinary files pay little (1,200 replacements in a 240,000-unit string), but a file inside the 1 MiB budget made of many short secret-like values, one `password=x` per line or many `ghp_` tokens, can spend seconds in a loop that neither cancellation nor the 2 s deadline can interrupt. The Safety Lens record already shows the shape: 562 ms without secrets against 1,712 ms with 16,800 concealments on 4–4.6 MB texts (`docs/validation/safety-lens-2026-10-05.md:59`). Merged ranges are replaced in reverse in an `NSMutableString` (`DefaultPrivacyFilter.swift:143-144`); each replacement moves the whole tail, so the loop is O(n·k), and it contains no `checkpoint()`. Only adapter ranges are capped at `maxJSONNodes` (`:66`, `EmbeddedSecretRanges.swift:186-187`); the filter's own assignment and value-pattern matches (`:105-132`) are not. The result is also bridged back as a UTF-16 `NSString` (`:145`), so later Swift passes over the safe text (`PreviewPipeline.swift:105`, `HiddenContentScanner.swift:37-38`, and the gutter's line index on the main thread at `LogicalLineNumberGutter.swift:36`) iterate a foreign string, which is slower (inferred). The fix is one forward pass that appends unconcealed segments and the token, checkpoints every few hundred ranges and returns a native string, plus a cap on the filter's own matches: fail as `:66` does for adapter ranges, or conceal the whole text as `SecretRangeBudget` does (security-privacy chooses). This touches AGENTS.md's "bounded, cancellable" rule and PLAN's ≤100 ms release target (`PLAN.md:535`); security-privacy should review the change.

**PF-05. The handler waits for the display.** The controller calls Quick Look's completion handler only after `display` returns (`PreviewViewController.swift:68-69`), so Finder presumably keeps the system's placeholder until preferences are read, the pipeline finishes and the whole synchronous display, styling and layout included, is done. Our loading state (`showLoading()`, `:37`) is therefore probably never visible in Finder, and decision 026's "spinner after 300 ms" (gate 2) would not appear there either; the self-audit's P1 ("Loading has no spinner in Finder") understates this. The display stage also cannot be cancelled: if the user presses an arrow key during a 200–400 ms display, the next `preparePreviewOfFile` waits for the main thread, so the ≤100 ms release target holds for the pipeline but not for this stage. Once PF-01 makes the first screen cheap, call the handler when the first screen is set or after a short deadline with the loading state, whichever comes first, and keep the remaining work in later run-loop turns; observe both orders in Finder before choosing. Only the call order changes; no window sizing or extra window is involved.

**PF-06. A soft hard timeout for thumbnails.** When Finder asks for many thumbnails at once, some small files can time out and draw the generic glyph, which the system keeps in its durable cache (`ThumbnailProvider.swift:10-11`). Each request builds its own pipeline so parses run in parallel (`ContentThumbnailService.swift:77-79`); each parse holds a cooperative thread synchronously until it finishes or reaches its 300 ms deadline; and the 1 s hard timeout is a `Task.sleep` on the same pool (`ThumbnailRace.swift:13-17`), as is the resumption that calls Quick Look. The repository has seen this: wall-clock tests including `aBlockedWorkerDoesNotDelayTheResult` and `aBlockedReadIsCutOffByTheHardTimeout` were moved to a serial pass because CPU-bound tests "held the shared thread pool past those deadlines" (`docs/validation/parity-program-2026-10-05.md:45`, `script/build_and_run.sh:66-70`). With as many blocked reads as cores, for example on a stalled network volume, no thread is left to fire the timer at all. "24 concurrent requests all complete" was observed on an 18-core host (`ContentThumbnailServiceTests.swift:310-320`). The fix: answer Quick Look from a Dispatch timer that needs no cooperative thread, bound concurrent parses per process, and learn on a Mac whether returning an error rather than a cached glyph is better when the cause is load. Decision 022's privacy rule is untouched; only scheduling changes.

**PF-07. Gate 11 is not measurable as written.** Gate 11 compares "text, JSON and CSV first content" against the native renderer benchmark (`026-world-class-ux-program.md:101`), but that benchmark has no CSV case (`benchmark_release_native_renderer.py:119-125`). Its numbers date from 2026-10-04, before the parity program added the findings banner, the hidden-content scan, the accessory bar, the info badge and live reload, and the 2026-10-05 entry lists Release performance as not verified (`CHANGELOGS.md:172`). Memory is sampled as `resident_size` and `ru_maxrss` (`:37-53`), which count clean, file-backed pages such as the CJK and emoji fonts the fixtures draw; the number that matters for an extension is `phys_footprint`, which the CAD worker already reads (`Native/CADWorker/main.cpp:27-34`). Finally, a 10 ms tolerance on a 200–430 ms p95 of 50 sequential samples is below the noise the record itself reports (Markdown p95 moved about 10 % with an unchanged median, `native-renderer-performance-2026-10-04.md:122-124`). The fix is R2; the lead should re-baseline the current main before the chrome workstream starts.

## Score against best-in-class

Score: 3 of 5. The architecture is right (a bounded, cancellable, off-main pipeline; real Release benchmarks with integrity checks; a viewport-bound gutter; measured optimizations already landed), but the renderer still does O(document) main-thread work before the first frame and on ordinary events, four of seven measured fixtures miss the 200 ms warm target by 16–234 ms, and nothing has been measured in a Quick Look host, cold, on macOS 15, on a smaller Mac, or as physical footprint.

A 5 in a Quick Look app means: in the signed extension on the slowest supported Mac, the first screen of a ≤256 KiB file appears within 100 ms warm and 400 ms cold, measured by signposts from `preparePreviewOfFile` to the first drawn frame; after that the main thread never blocks for more than one frame, because off-screen layout and styling happen incrementally; mode switches and returning to Source take under 50 ms; holding an arrow key through 20 files never queues; one ordinary preview adds under 50 MiB of `phys_footprint` and returns to baseline when closed; a 200-file folder produces no load-induced timeout glyphs on an 8-core Mac; a growing log reloads in under 10 ms per append; and a CI job rejects a change that adds a full layout pass or a measurable median regression.

## Open questions for the owner

1. Which Mac and macOS version define the targets? All evidence comes from an 18-core M5 Pro on macOS 27.2; gating on the slowest supported Mac and on macOS 15 changes the thresholds and the order of R3 to R9.
2. May the scroller be approximate for a fraction of a second after a large file opens? Viewport-first layout (R5) needs that; an exact thumb from the first frame means laying out the whole file first, which is today's cost.
3. May the extension answer Quick Look before content is ready and show its own loading state? Decision 026's 300 ms spinner can only appear in Finder if it does (R8).
4. Evidence for the pending decisions, not a recommendation. Opening JSON in Outline would skip source layout on first display: Summary-first ZIP and SQLite finish their initial stage in 16.2 and 28.6 ms warm p95 against 380.7 ms for JSON's Source stage (`docs/validation/native-renderer-performance-2026-10-04.md:110-114`), and the outline model is already built either way; the JSON outline has more rows than those summaries, so the comparison is indicative only. For opt-in 3D thumbnails, CAD imports took 0.52–1.11 s in single observations (`docs/validation/cad-previews-2026-10-04.md:20`) and the largest admitted 3MF parsed in 1,344 ms with a 270 MiB process peak (`docs/validation/mesh-2026-10-05.md:65`), against a 1 s thumbnail hard timeout, and the renderer compiles its shader for every backend (PF-15); only small meshes would fit. For the website's STEP claim, the 512 MiB footprint guard and 15 s CPU limit mean large STEP files fail by design.
