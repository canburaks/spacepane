# Platform integration and release readiness review — 2026-10-06

Reviewed from source and the repository's own validation records, on Linux, on 2026-10-06. Nothing was compiled, signed, installed, run or measured, so every statement about Finder, Quick Look, App Store processing or macOS 15 is inferred from code and records unless a cited record observed it. The dimension covers the preview and thumbnail extension hosts and their lifecycle, what each Finder surface does with them, the open M0 gates, the App Group settings snapshot, provider conflicts and diagnostics, the CAD XPC service, signing and archive checks, macOS 15 versus the Liquid Glass releases, App Store readiness and the website's honesty about the app. Verdict: the host code is thin, fail-closed and well contained, but the proof that it works where users meet it rests on one macOS 27.2 host, a retired bundle identity and 21 of 76 formats, so the UX program has to begin with a Mac pass rather than end with one.

## Current state

The platform layer is better engineered than its evidence. Strengths to preserve:

- **Request ownership in the host.** `preparePreviewOfFile` cancels the previous request, stops live reload, shows a state and runs one task whose result is applied only while `activeRequest?.id` still matches (`Extensions/PrevPreviewExtension/PreviewViewController.swift:32-75`). One main-actor gate calls Quick Look's handler exactly once on success, replacement, disappearance and deinit (`:20`, `:100-105`, `:152-165`). Metal and MIDI suspend on disappearance, and visibility is host-managed because the remote backing window reports occluded while shown (`:22-30`, `:77-98`; `docs/validation/cad-previews-2026-10-04.md:36`).
- **The host owns the window.** There is no `preferredContentSize`, no `#available` branch anywhere, and the shared renderer touches the window only through `makeFirstResponder` (search of `PreviewRenderers`). The view's shortcuts are Command combinations only (`Interaction/PreviewShortcut.swift:19-26`); Escape is handled solely by the Go to Line and filter fields while they have focus (`GoToLineBar.swift:116`, `OutlineFilterBar.swift:88`), and Space and the arrows are left to Quick Look.
- **Fail-closed settings with two distinct messages.** A missing or reserved App Group shows a configuration message before any read (`PreviewViewController.swift:39-43`; `PreviewRenderers/HostedConfiguration.swift:44`); a corrupt, unreadable or newer snapshot shows settings-unavailable (`PreviewViewController.swift:50-58`); thumbnails fall back to the glyph in both cases (`PreviewThumbnails/ContentThumbnailService.swift:31-35`). The 2026-10-03 field failure was diagnosed exactly this way (`docs/validation/shared-settings-configuration.md:9`).
- **A careful snapshot.** Bounded `O_NOFOLLOW` regular-file reads of at most 64 KiB (`PreviewPreferences/BoundedPreferencesData.swift:12-22`), strict per-schema decoding from 1 to 6 that defaults only fields a schema lacked (`PreferenceStore.swift:34-65`), unknown versions fail closed (`:65`), atomic replacement (`:91`), one companion writer that drains to the newest revision (`Apps/PrevApp/Stores/CompanionSettings.swift:142-165`), and a fresh read on every extension request and reload (`PreviewViewController.swift:48`, `:120`), so no stale in-process copy exists.
- **Manifests derived from one catalog and checked twice** (`script/sync_manifests.py`; `script/validate_project.py:168-179`). The preview declares four types the thumbnail does not (`public.data` and the three system mesh types); `public.data` is preview-only and enforced (`validate_project.py:117-125`; `Configuration/Preview-Info.plist:1222`); third-party aliases are never canonical, imported or exported (`validate_project.py:133-138`).
- **CAD containment.** The preview links only an XPC client; the service holds App Sandbox and nothing else (`Configuration/CADImportService.entitlements:5`), sets a peer signing requirement, cancels on invalidation and runs at most two imports (`Native/CADImportService/main.swift:8-18`; `PreviewCADFormats/CADImportService.swift:25`); the helper is signed `<owner>.CADWorker` with sandbox and inherit only (`script/embed_cad_worker.py:33-36`; `script/check_release_archive.py:93-100`).
- **Release tooling.** `validate_signing.py` refuses placeholder identities before a signed run; `--archive` unregisters Xcode's intermediate copy so it cannot compete in Finder (`script/build_and_run.sh:128-135`); `check_release_archive.py` checks store keys, icon, quarantine, architectures, deep signature, sandbox, network and temporary exceptions, helper identity, OCCT notices and dSYMs.
- **Honest diagnostics.** The provider scanner reads only property lists, never follows links and is bounded (`Apps/PrevApp/Models/QuickLookProviderScanner.swift:35-42`, `:231-292`); its guidance says it cannot tell which provider Finder uses; the info badge names the provider only while content is shown (`NativePreviewView.swift:505`, `:519-523`).
- **Candid records.** Recent records list what they did not observe (`docs/validation/thumbnails-2026-10-05.md:3`, `parity-program-2026-10-05.md:66-72`, `interaction-2026-10-05.md:36-38`), and earlier host passes avoided cache resets and Finder restarts while documenting stale registrations (`extensionless-files-2026-10-04.md:36-46`).

**PI-02. The CAD peer requirement probably rejects the store-signed extension.** The service builds `anchor apple generic and identifier "<preview>" and certificate leaf[subject.OU] = "<team>"` (`Native/CADImportService/main.swift:33`) from the `CADAllowedClient*` build values (`CADImportService-Info.plist:5-8`). Apple Development and Apple Distribution certificates carry the team in the leaf's OU, which is why every observation passed. Builds delivered through the Mac App Store and TestFlight are re-signed by Apple with a certificate shared across developers; the team then lives in the code directory, and Xcode's own designated requirements for store builds accept the Mac App Store marker (`certificate leaf[field.1.2.840.113635.100.6.1.9]`) instead of the OU (inferred from Apple's distribution scheme, not observed here). If so, every STEP and IGES preview in the shipped app ends in the importer-unavailable state, and nothing local can catch it: the archive check and the Organizer export both see the developer's own signature (`app-store-submission.md:22-28`). Fix: accept either branch, `anchor apple generic and identifier "<preview>" and (certificate leaf[field.1.2.840.113635.100.6.1.9] /* exists */ or certificate leaf[subject.OU] = "<team>")`, or derive the requirement from the service's own designated requirement with the identifier swapped; prove it on a TestFlight install (step I3). Rule: AGENTS keeps the accepted-client requirement; this keeps it and makes it correct for the release channel.

**PI-03. macOS 15 is promised and untested.** No record ran anything on macOS 15 (`installed-host-2026-10-04.md:29` and every record since), and Intel is excluded by design (`Base.xcconfig:12-14`). The risks, most serious first: `isolated deinit` appears in 9 production files (for example `PreviewViewController.swift:20`, `PreviewLiveReloader.swift:41`) and relies on a concurrency-runtime entry point that I believe first shipped with the Swift 6.1 runtime in macOS 15.4; `--check-compiler` is only a typecheck, so whether Xcode 27 back-deploys it to 15.0 has to be read from the binaries and proven by a launch on 15.0–15.3, because a strong import of a missing symbol would stop the companion and both extensions from loading. The mode control is pinned to 26 pt (`NativePreviewView.swift:612`), which must be checked against both control generations. The System Settings deep link is marked unverified on 15 (`GeneralView.swift:154-156`). Quick Look's chrome differs between 15 and 26 (baseline A2), which feeds the width thresholds. Fix: symbol inspection in step B2 and phase K on a second Mac or VM through TestFlight; if 15.0–15.3 cannot load the build, choose between a higher `LSMinimumSystemVersion` and removing `isolated deinit` (owner question 4). Rule: AGENTS "macOS 15 is the deployment baseline".

**PI-04. The extension's loading state is probably invisible in Finder.** The controller sets a loading state (`PreviewViewController.swift:37`) but calls Quick Look's handler only after preferences and the whole pipeline finish (`:63-69`). Quick Look presents a view-based preview once the handler is called, so users most likely see Quick Look's own wait state for the entire pipeline, which can approach the container scan's 5 s budget (`parity-program-2026-10-05.md:30`) or the CAD 20 s deadline (`cad-previews-2026-10-04.md:9`); whether Quick Look abandons a slow handler is undocumented. Decision 026 gate 2 ("loading shows a spinner after 300 ms", identically in Finder, `026-world-class-ux-program.md:92`) therefore cannot be met by renderer work alone, and the self-audit's "Loading has no spinner in Finder" understates the issue. Fix: decide the completion policy before ux-chrome builds `NativeStateView`: complete once the state view is installed or after a short grace period, keep resolving failures with `nil` as today, and verify with step D5 (R2). Owner: the lead, because the host file has no workstream. Rule: baseline principle 7; HIG Loading.

**PI-05. Content-free system types are registered for thumbnails.** The thumbnail extension declares 276 types, among them `public.folder`, `com.apple.application-bundle`, `com.apple.disk-image-udif`, `com.apple.installer-package-archive`, ZIP, TAR, 7z, RAR, torrents and MIDI (`Thumbnail-Info.plist:1478-1489`). The catalog gives 31 formats the `generic` policy, and `.app` and `.ipa` a `content` policy that draws the bundle icon (`017-package-and-certificate-inspection.md:11`; my catalog grouping). The glyph is one light page with three rules for every type (`ThumbnailRenderer.swift:14-27`). Wherever macOS has no thumbnail generator of its own and picks this provider, icon view, Gallery and Spotlight would show that page instead of distinct system icons, and the result sits in the durable cache the product deliberately never clears (`022-content-thumbnails.md:56-58`). For text-conforming types the glyph protects secrets; for folders, apps, disk images, installers and archives the system icon is already content-free, so the registration costs recognisability and buys nothing, and decision 017 itself doubts `.app` routing (`:82`). Fix: observe first (step H2), then move content-free binary types to `none` (owner question 2). Rule: AGENTS "respect system/provider selection".

Fix: a short host spike (step D4) with a throwaway popover and the existing shortcuts before ux-chrome starts, and an inline disclosure fallback written into contract 1 (R9). Rule: baseline anti-pattern "tooltip-only explanation"; principle 8.

**PI-08. The OS requirement omits Apple silicon.** Release 1.0 builds arm64 only (`Base.xcconfig:12-14`; `app-store-submission.md:71`), yet `hero.chip` says "Quick Look extension for macOS 15+" (`home.json:9`), `how.steps.install.body` "It runs on macOS 15 Sequoia and later" (`home.json:27`), `faq.items.macos.answer` "macOS 15 Sequoia or later" (`home.json:590`) and `subtitle` "Help with SpacePane for macOS 15 Sequoia and later" (`support.json:7`); the static pages repeat it (`Website/index.html:41`, `:66`, `:358`; `Website/support.html:33`). macOS 15 and 26 run on Intel Macs. **PI-09. The OCCT route is open.** The audit records that static OCCT linking leaves "library-source and applicable relinking obligations" and that release "remains blocked on a reviewed distribution route" (`docs/dependencies/occt.md:58-66`, `:80-88`); the PLAN box to decide CAD for 1.0 is open (`PLAN.md:519`). Owner question 1 (R11). Rule: AGENTS dependency licensing gate.

**PI-10. No privacy manifest.** No `PrivacyInfo.xcprivacy` exists, and the code uses API categories Apple lists as required-reason APIs: file timestamps (`stat`, `fstat`, `lstat`, `fstatat`, for example `PreviewFormats/Containers/FolderScan.swift:180` and the snapshot reader), system boot time (`ProcessInfo.systemUptime`, `PreviewRenderers/NativeMIDIPlayback.swift:32`) and user defaults (`Apps/PrevApp/Stores/CompanionPreferences.swift:14-17`). Fix: one manifest each for the app, preview, thumbnail and CAD service with no tracking, no collected data and reasons to confirm against Apple's current list (candidates: C617.1 and DDA9.1 for timestamps, 35F9.1 for uptime, CA92.1 for defaults), checked by `validate_project.py` and the archive check (R6). Rule: M6 release gate.

**PI-11. **Host width, safe area and the Tahoe questions (PI-15, PI-16, PI-23).** `view.bounds` at `preparePreviewOfFile` time is the 800 × 600 placeholder from `loadView` (`PreviewViewController.swift:23`), so it is not a host width; the renderer already re-measures in `layout()` (`NativePreviewView.swift:442-445`), which is where the compact density should be decided, from its own bounds with hysteresis, so the controller need not report anything. Nothing in the host can size the window except possibly that placeholder frame, which step D2 settles. The header pins to `topAnchor` (`NativePreviewView.swift:156`); offscreen renders and 27.2 Finder sessions showed the header, but no record measured a top safe-area inset or scrolled content under a glass title bar (baseline A8 item 9). The companion opts out of the system sidebar material with an opaque `windowBackgroundColor` and a hidden title bar (`CompanionSidebar.swift:26-30`; `CompanionStyle.swift:35`; `CompanionApp.swift:26`), and no code branches on macOS 26. **Provider conflicts (PI-18).** The scanner is sandbox-safe in design: read-only bounded plist reads, no links, real home from the account database, unreadable folders reported rather than hidden (`QuickLookProviderScanner.swift:76-85`, `:225-292`), consistent with AGENTS and decision 023 (`023-settings-schema-6-color-schemes-and-provider-diagnostics.md:103-109`); whether the signed sandbox lets it list `/Applications` is still unobserved. macOS exposes no public API that names the selected provider: System Settings → General → Login Items & Extensions → Quick Look shows per-extension switches, `pluginkit -m -A -D -v -p com.apple.quicklook.preview` lists registered copies with paths and election state (Terminal only, never from the sandboxed app, never `-e` in tests), `lsregister -dump` shows which product's type declaration won a suffix (the `.jsonl` and `.env` cases), and `qlmanage -m` concerns legacy generators that no longer load on macOS 15 (baseline A5). Apple's built-in text preview, the likely provider for `.txt` and `.swift` in the matrix, declares nothing the scan can read. An honest per-type marker states only what the scan found: "Also declared by AppName's Quick Look extension", with the hint "macOS chooses one provider for each file type. If previews of this type look different, check System Settings → General → Login Items & Extensions → Quick Look", and a footer naming the scan time and saying that apps elsewhere and Apple's built-in previews are not included. Avoid "conflict", "handled by", "overridden" and any green.

**Support and diagnosis (PI-14, PI-24).** There is no crash SDK, which is right for privacy; Apple's opt-in crash reports are the only telemetry and the privacy page says so. The extensions log nothing, `PREV_FEEDBACK_URL` is empty (`Configuration/Branding.xcconfig:20`) and the support address has no mailbox yet, so a user's only bug channel does not work today and a report would contain no diagnostic facts. A privacy-safe "Copy diagnostics" in About (R15) plus debug-level host events (R4) close that without collecting anything.
