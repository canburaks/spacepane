# SpacePane — repository guidance

## Purpose and current scope

SpacePane is a local macOS Finder Quick Look preview and thumbnail app with a companion setup and customization application. Its website is spacepane.com. Prev was the working name; it survives only in technical names (the repository, Xcode project, targets, source directories and the `PREV_` build-setting prefix), which are not branding. The product targets macOS 15 or later. Preparation for Mac App Store publication began on 2026-10-10 at the owner's request (see the [publication plan](docs/plans/2026-10-10-app-store-publication-plan.md)); builds 1.0.0 (1) and (2) were uploaded to App Store Connect for internal testing and will not be submitted; build 3, the first without STEP and IGES, was submitted for review by the owner on 2026-10-13 under the [review readiness plan](docs/plans/2026-10-12-review-readiness-plan.md) and is waiting for App Review; acceptance is not established. Implementation now includes 81 cataloged logical types in the product (74 in build 3; [decision 030](docs/decisions/030-safety-lens-3-models-add-ons-and-packages.md) added seven model-file, add-on and package formats on 2026-10-14), native safe source/outline/Markdown presentations, bounded containers/SQLite, MIDI controls and the formats and modes added by the [competitor parity program](docs/decisions/025-competitor-parity-program.md). These are implementation capabilities, not a claim of verified Finder routing or release readiness. See the [parity validation](docs/validation/parity-program-2026-10-05.md) and the earlier [expansion validation](docs/validation/parallel-expansion-2026-10-04.md).

The user chose the name on 2026-10-04 and may rename the app again. Treat visible branding as replaceable: centralize app/extension display names in build configuration and a small shared branding resource, and pass the name into localized copy rather than scattering literal `SpacePane` strings. Keep reusable modules, stable format IDs, preferences keys and persisted data independent of the display name. Once chosen, bundle/App Group identifiers are technical identities, not values to regenerate on a branding change; changing them requires a separate compatibility/migration review. Do not invent production identifiers before they are supplied or agreed.

## Baseline constraints

- Use modern Quick Look app extensions; macOS controls Finder routing and the Quick Look host window.
- Keep processing local, read-only, bounded, cancellable, and safe for untrusted files. Do not run scripts embedded in previewed content.
- Never promise previews for missing bytes or control of provider priority. Files without an extension are supported as text through one exact `public.data` declaration in the preview extension only; follow [the extension-free files decision](docs/decisions/011-extensionless-files.md). Executable-bit files and thumbnails for these files are not covered.
- Redact likely secrets by default. Keep sensitive content out of thumbnails, logs, durable caches, and sample files.
- Keep a native UI and accessible text selection, keyboard navigation, adaptive appearances, and explicit fallback states.
- The companion has one app-owned window with a fixed sidebar for every screen: General, File Types, Theme and About. The user explicitly replaced the earlier separate Settings-window convention and, later, the grouped tabs. Do not add Settings scenes, WindowGroup instances, detached previews, About panels or auxiliary app windows. Menu commands and shortcuts select destinations in the same singleton window. Follow [the single-window decision](docs/decisions/005-single-window-tabs.md) as amended by [the sidebar redesign](docs/decisions/010-companion-sidebar-redesign.md).
- Developer Mode is a companion-only choice, off by default, that reveals Try Preview, Open File and its shortcut. Keep it out of the shared extension snapshot; it must never change preview or thumbnail behaviour. Companion status text reports where settings are saved, never that Finder uses this provider.
- Users must be able to enable or disable each shipped logical file type. Follow [the file-type controls decision](docs/decisions/002-file-type-controls.md): catalog-driven Settings, persistent stable IDs, and one policy shared by previews, thumbnails and the companion. A disabled type must not bypass the choice through generic text/source fallback. These controls do not promise a change in macOS provider selection.
- Audit third-party licenses and extension safety before adding dependencies. Researching a project does not authorize copying its implementation.
- **Version 1.0 ships without IGES and STEP** ([decision 028](docs/decisions/028-no-cad-in-version-1.md), owner, 2026-10-13): their importer links Open CASCADE Technology under the LGPL and the licence question is not cleared. `PREV_INCLUDE_CAD` in `Configuration/Base.xcconfig` is `NO`: the product contains no `CADWorker`, no `CADImportService.xpc` and no `OCCT-Notices`, the two catalog entries live in `Configuration/CADFormatCatalogEntries.json` instead of the catalog, and `script/check_release_archive.py` refuses an archive that carries any of them. Do not set it to `YES`, restore the entries or mention these formats in store copy without a recorded licence clearance from the owner. The CAD sources, tests and build scripts stay in the repository; the rest of this paragraph describes them for the day they return.
- IGES (`.igs`/`.iges`) and STEP (`.step`/`.stp`) use independent default-off controls per the user’s performance requirement. Follow [the opt-in implementation decision](docs/decisions/006-opt-in-cad-previews.md); keep kernel import in the disposable byte-only helper and Metal creation lazy. Finder uses the independently sandboxed, embedded XPC service because direct child launch is denied; keep its accepted-client signing requirement and connection-owned cancellation. Remote Quick Look visibility follows controller lifecycle, while the companion retains window-occlusion cleanup. Static dependency licensing and broader platform coverage remain separate gates. The 3D previews are explicit requirements; follow [the CAD feasibility and scope record](docs/initial/07-cad-preview-feasibility.md) and the CAD checklist in PLAN. The catalog now includes both CAD types; check the validation record before claiming host or release support. Keep the supplied CAD model private and outside repository fixtures. Preserve the bounded neutral geometry capability and separately audited importer; metadata inspection or text fallback does not satisfy 3D preview acceptance.

## Working without a compiler

Most sessions run in a cloud container with no Swift toolchain. [Decision 027](docs/decisions/027-best-in-class-quality-program.md) sets the rule: a cloud session authors and never verifies; a Mac session (or the macOS job of `.github/workflows/package.yml`, dispatched by hand) compiles, tests, observes and owns every checked plan box. Every Swift change made without a compiler is appended to [the pending-verification queue](docs/validation/pending-mac-verification.md) and its changelog entry says "authored without a compiler; verification pending" until a Mac session replaces that sentence with evidence.

Rules for Swift written blind:

1. Use only APIs that already have a call site in this repository, or that Apple documents as available on macOS 15 with an unchanged signature. The sources contain no availability checks; never introduce one blind. A first use of an API new to the repository goes in its own small commit behind a narrow wrapper and is flagged in the queue.
2. Mirror the repository's concurrency patterns exactly: `@MainActor final class` for anything that touches AppKit or SwiftUI, `@MainActor @Observable final class` for stores, nonisolated `Sendable` value types for models, `isolated deinit` for teardown, `@concurrent` for blocking work, `Mutex` for shared state. The package's default isolation is `nonisolated`, so a missing annotation is a defect.
3. Keep blind edits inside one module. Cross-module access changes, `Package.swift` target changes, resource moves and `Prev.xcodeproj` edits wait for a Mac.
4. After adding an enum case, find every `switch` over that enum and update each; the compiler cannot remind you.
5. Keep SwiftUI bodies small and extract subviews.
6. Tests first, in their own commit, against named seams and pure models, with explicit locales; on the Mac, run them against the old code to see them fail for the right reason.
7. One concern per commit, about 300 changed Swift lines at most; run `./script/build_and_run.sh --check-static` and `tools/check_swift_syntax.py` before each push; append the queue row.
8. Never add a test that waits on wall time; inject the clock or scheduler.
9. Strings go through `tools/add_localizations.py` (or a workstream additions file under `tools/localization/additions/`) with translator context and a plural form where a count appears; never a literal in a view.
10. Prefer additive changes; when an existing method must change, keep the old path intact behind the new call until a Mac session has validated the replacement.

Parallel agents own disjoint files (`tools/ownership.json`, checked by `tools/check_ownership.py`); the lead owns the shared contracts, the catalogs, the typed strings enum, the plan, the changelog and integration.

## Architecture and implementation rules

### Highest priority: modularity and inexpensive format additions

Treat modular design and separation of concerns as the primary architectural requirements. Follow [the format extensibility decision](docs/decisions/001-format-extensibility.md) and the corresponding section of [PLAN.md](PLAN.md).

- **Separation of concerns / single responsibility:** keep format detection, parsing, file access, request orchestration, privacy policy, presentation models, rendering and host integration distinct. Each component should have one coherent reason to change; avoid both giant managers and meaningless one-function modules.
- **Open/closed:** a new format that uses an existing presentation should normally require its adapter, catalog/registration entry and fixtures, without modifying the pipeline, host controllers or unrelated adapters. A genuinely new presentation capability may justify a small shared-contract change with a documented reason.
- **Dependency inversion:** define small contracts at the domain boundary. Orchestration depends on those contracts, not concrete decoders or UI frameworks. Inject concrete adapters/services at the app/extension composition boundary; do not use a global service locator.
- **DRY:** maintain one format catalog for supported-type metadata and derive or validate manifests/help against it. Share actual common reading, budget, privacy and rendering behavior. Do not duplicate parsers between the companion, previews and thumbnails, or force unrelated formats into one abstraction merely because their code looks similar.
- **KISS:** prefer explicit registration, composition, plain value types and a few focused protocols over inheritance hierarchies, reflection, auto-discovery or a general-purpose dependency-injection framework.
- **YAGNI:** implement boundaries needed by real baseline formats. Do not build downloaded plugins, a public plugin SDK, a stable external ABI, speculative hooks or one package per suffix. Split dependency-heavy format families when an actual isolation/build/resource need appears.
- Follow [binary input and safe-presentation boundaries](docs/decisions/007-binary-inputs-and-safe-presentations.md). Text, binary, bounded random-access and directory adapters share the policy/privacy pipeline. The small `SQLiteSafetyShim` target wraps only public variadic SQLite configuration calls; it is an internal dependency, not a new public product.
- Follow [the safety findings decision](docs/decisions/012-safety-findings.md). Findings are typed kinds, counts, displayed lines and typed details, never source values; the one exception is privacy-filtered text decoded from Unicode Tags. Anything that reports lines scans the concealed displayed text and numbers lines with `LogicalLines`. A new finding kind needs its enum case, wording, strings in every app language and fixtures. Shared classifiers (`HiddenCharacters`, `SecretFieldPolicy` patterns and token) have one owner.
- Keep low-level parser dependencies inside the owning adapter module. Vendor parser types must not leak into domain contracts, settings or views. Keep UI types out of parser contracts and avoid dependency cycles.
- Every catalog format has one built-in appearance sample for the Theme page's live preview. Add it in `script/generate_appearance_samples.py` with the format; `--check` fails when the catalog and samples differ. Samples are synthetic, bounded, free of secret-like values and read through the normal pipeline.
- Every format addition must use the existing budget, cancellation, redaction and fallback pipeline, plus shared conformance tests. Document any unavoidable shared-core edit and its effect on existing formats.
- Follow [the JSON Lines extension record](docs/decisions/004-json-lines-and-group-controls.md) for the first incremental format addition: retain cumulative parser budgets, source encoding provenance and independent format identity when sharing a parser. Explicit imported UTTypes and optional system aliases are catalog metadata; never make generic type construction a catch-all fallback.
- Generate file-type settings rows from the same catalog. Keep enablement independent of decoder identity; apply the central policy after bounded classification and before content parser construction. Do not put preference reads or toggle UI in each adapter.
- If a principle conflicts with correctness, platform restrictions or measured performance, choose the smallest justified exception and record it in the plan/decision record and changelog. These principles guide design; do not use them to justify premature generalization.

### Strings, resources and code references

- Multilingual support is a product requirement from the first implementation. Internationalize every app-authored user-visible string across the companion, preview extension and thumbnail extension. This includes menus, settings, onboarding, help, format descriptions, tooltips, placeholders, loading/empty/disabled/error states, accessibility labels/hints, notifications, copy/export status and text drawn into graphics. Localize bundle metadata and system-facing descriptions where supported. English-only resources or pseudolocalization alone do not satisfy shipping multilingual support.
- Do not scatter hardcoded strings through application logic or views. Define values once at their owning resource/configuration/schema boundary and consume named, preferably compiler-checked references.
- Put user-facing text, including errors, accessibility labels, menus and help, in String Catalog resources. Use generated typed accessors when supported by the selected toolchain, otherwise a small typed localization API. Resolve resources from their owning bundle so the companion and both extensions work independently. Use localized interpolation/pluralization and locale-aware formatting rather than concatenating translated fragments.
- Use enums or small typed IDs for formats, modes, actions, routes and domain errors. Prefer actual symbols, key paths, typed selectors and framework constants over string-based dispatch or repeated raw API names. Parsers return typed results/errors; presentation code supplies localized wording.
- Reference assets through generated symbols where available; wrap string-only APIs such as symbol names in narrowly owned named definitions. Reference types through `UTType` values and the shared format catalog, settings through typed models/keys, and branding/build identity through their established configuration. Derive file locations through authorized URLs and platform directory APIs, never machine-specific absolute paths.
- Literal definitions remain necessary in catalogs, schemas, configuration and protocol adapters. Keep format suffixes, wire/schema keys and persisted raw values at those boundaries, preserve compatibility, and never localize technical identifiers or user file contents. Independent test expectations may contain literal values so tests can catch an incorrect production constant.
- Keep definitions with the module that owns their meaning; avoid a global catch-all `Constants` file and redundant wrappers around already typed APIs. Check references and localization/resource availability during review and builds; do not treat a blanket ban on every string literal as a useful substitute.
- Keep presentation locale and language separate from file parsing. Localize human-readable dates, numbers, byte counts and durations; preserve exact source values, code, filenames, paths and protocol identifiers. Never translate or reformat file contents merely because the UI language changes. Map raw system/parser errors to localized domain messages instead of showing unreviewed debug text.
- Design for plural rules, reordered placeholders, text expansion, Unicode and right-to-left layout. Use semantic leading/trailing alignment; do not blindly mirror source code, timelines or other direction-sensitive content. Add translator context and verify accessibility in every shipped language. Resolve a documented development-language fallback without displaying resource keys, and test resource lookup in all three bundles.
- The chosen language set is English plus Turkish, German, French, Simplified Chinese, Japanese, Hindi, Kurmanji Latin, Russian, Indonesian, Bengali, Hausa, Portuguese and Spanish. Follow [the language/transfer decision](docs/decisions/008-languages-and-appearance-transfer.md) and `tools/localization/languages.json`; exact key coverage and draft translation status do not replace native-speaker review. Do not infer languages from the developer's location. Each advertised language needs complete, reviewed translations and UI validation. The policy file separates the two sets: `languages` is the chosen set, whose draft translations stay in the repository and in the package's resource bundle; `shipped` is what a build carries and the store advertises. A language other than the development language enters `shipped` only with a record in `reviews` naming its reviewer and date. `script/build_metadata.py` generates top-level bundle metadata for shipped languages only, the three Info.plists list them in `CFBundleLocalizations`, and `script/check_release_archive.py` refuses an archive whose app or extensions carry any other `.lproj`. The build prunes the drafts from the nested `PreviewCore_PreviewRenderers.bundle` of the app and both extensions (`script/prune_resource_languages.py`, a run-script phase per target), and the archive check refuses any non-shipped `.lproj` there: the host-bundle language rule kept them unreachable in the companion (observed on macOS 27.2, 2026-10-12) but not in a copy of either extension used as the main bundle ([record](docs/validation/nested-language-pruning-2026-10-17.md)). Version 1.0 ships English only. Verify effective language selection in real Finder hosts separately from companion localization; never claim cross-process language behavior from a companion-only test.

### Platform and runtime boundaries

- Use an Xcode host app and embedded preview/thumbnail extension targets; keep reusable library logic and unit tests in SwiftPM. A successful `swift build` does not validate extension installation, signing, entitlements or Finder routing.
- SwiftUI owns companion scenes/settings and small composed UI. Use narrow AppKit adapters for the Quick Look controller, rich selectable text, dense outlines/tables and platform behavior that needs them.
- Separate request/file access, parsing, redaction, presentation models and rendering. Share the same core pipeline with the companion's direct preview so it remains useful when Finder selects another provider.
- Plan explicit Swift 6 language/concurrency settings at scaffold time. Inspect actual manifests/project settings before changing isolation. UI state belongs on the main actor; parsing and blocking I/O do not. `async` alone is not an off-main guarantee.
- Keep parser state confined to one request or worker owner; pass immutable Sendable results. Do not silence concurrency diagnostics with unchecked annotations without a documented invariant and focused validation.
- Each request owns cancellation, resource budgets, generation identity and file-access lifetime. Late results must not update a replacement preview. Bound input, output, depth, nodes, entries, cells, decoded pixels and parser work before allocation.
- Read source files without mutation. SQLite WAL/sidecar access needs a demonstrated no-source-write path; do not apply `immutable=1` to a mutable live database. Reject unsupported locked/inconsistent states clearly.
- Do not extract archives to the source directory, follow symlink escapes, recurse into nested archives by default, run notebook cells or package scripts, or execute document-supplied JavaScript.
- Prefer native Markdown. If a web renderer is adopted after a measured prototype, sanitize app-generated content, prohibit remote resources and document scripts, use nonpersistent storage, and test subresources as well as navigation.
- Extension settings are validated, versioned App Group snapshots. The companion is the persistent writer. A currently displayed Finder preview or cached thumbnail is not guaranteed to refresh immediately.
- Appearance schema 5 adds bounded named profiles and inert appearance-only theme transfer. The companion may use user-selected write access solely for explicit exported files; extension source permissions remain read-only. Readers never write preview sources.
- Themes and imported preferences are inert schema-validated data. Typography controls must tolerate unavailable fonts and unsupported traits, and provide reset and accessible contrast variants.
- Logical line numbers describe the already-concealed displayed text. Keep their gutter outside selectable text so copying and finding preserve safe source characters; never imply original line positions after multiline concealment. Migrate every persisted appearance field strictly, defaulting only newly introduced fields.
- Follow [the appearance decision](docs/decisions/003-preview-appearance.md): appearance-only changes restyle safe presentations without source I/O; format-policy changes retain cancellation and disabled-content enforcement. Keep semantic syntax hints separate from format identity and never color unredacted source.
- Preserve exact safe source code units when invalidating text and derived presentation models; Swift's canonically equivalent String equality alone cannot detect every source replacement. Hidden source styling may be deferred, but replacement generations must clear stale text and revealing Source must apply current appearance. Keep native outline expansion/selection and reusable-cell accessibility metadata covered by the renderer regression tests.
- Use explicit supported content types and respect system/provider selection. Do not export ownership of another developer's type, rewrite signed manifests at runtime, or add generic root types. The single exception is `public.data` for the extension-free text format: preview only, never thumbnails, exact type and no suffix, and never a conformance ancestor. `public.item` and `public.content` stay prohibited.
- Follow [the direct-file-drop contract](docs/decisions/006-direct-file-drop.md): accept one native local file URL, inspect only metadata during hover, retain the original URL and use `PreviewSession.open`. Reject multiple/web/ambiguous drops without replacing the current preview. Private-pasteboard tests never use the user's general clipboard and do not prove signed Finder drag grants.
- macOS 15 is the deployment baseline. Gate newer APIs and verify against the selected SDK; toolchain version and host OS do not change the product minimum automatically.

## Verification and completion

For each new renderer, add meaningful normal, malformed, oversized, cancellation, no-source-mutation and privacy fixtures. Use synthetic secrets and licensed redistributable fixtures only. Verify VoiceOver, keyboard access, copy behavior, Unicode, appearance, and fallback states in both the companion and Finder host.

Measure performance with recorded Release configuration and hardware. The budgets in the plan are targets until measured. Track cold and warm requests separately and count any web/helper process memory. A deadline does not forcibly preempt noncooperative native code.

For file-format support, record parser support, declared/resolved UTType, observed Finder preview, observed thumbnail, tested OS and restrictions separately. A companion preview or `qlmanage` result does not prove all Finder surfaces use this provider.

During scaffolding create `script/build_and_run.sh` and `.codex/environments/environment.toml` using the build-macos-apps bootstrap skill. Run the relevant SwiftPM tests and Xcode integration checks only after real targets exist. Use clean installed/signed builds for extension lifecycle checks. Do not alter system extension preferences, reset shared Quick Look caches or kill Finder merely to conceal a routing defect.

Before adding a dependency, pin a revision/version, inspect transitive licenses and notices, confirm public extension-safe APIs and macOS 15 support, and document the update/security owner. Do not bundle a legacy generator or private-framework implementation as a shortcut.

Before App Store submission, recheck current Apple policies, signing/entitlements, privacy declarations, dependency licensing, screenshots and advertised format coverage. Publication preparation is now an active milestone, but uploading, submitting and releasing happen only on the owner's explicit instruction. Keep App Store Connect API keys and other credentials out of the repository, and keep monetization and store metadata out of format adapters and Quick Look rendering.

Country-specific prices are required. App Store Connect owns effective prices and storefront availability; the repository records intended pricing policy, release checks and any future typed purchase-product references. Do not embed a live country-to-price table or infer purchase country from UI language, device locale or IP. If in-app purchases are introduced, display prices from StoreKit product data and keep commerce out of format adapters and Quick Look rendering. Country pricing alone does not introduce subscriptions, feature tiers or a need for an in-app purchase module. Follow [the pricing boundary in the plan](PLAN.md#country-specific-pricing).
